Benchmarks

The same test files, unchanged, run by vynta, Vitest and Jest. Every time is the whole command, from starting it to its exit: what you wait for in your terminal and on CI.

Summary

2.7×faster than Vitest 5 on a library suite
5.5×faster than Jest 30 on the same suite
2.6×faster than Vitest 5 with coverage
2.9×faster than Jest 30 on a large backend suite

A library suite

The tests of schiva, a schema validation library: 39 files, 981 tests, CommonJS, written for Jest (describe, it.each, jest.spyOn, .rejects...). Every runner passes all of them.

A backend suite

A private Express and MongoDB backend: 79 files, 1,218 tests, 38 jest.mock() calls, an in-memory MongoDB for every end-to-end file, Jest 30 with the project's own settings (--maxWorkers=4). The tests ran unchanged, and every runner passes all of them.

Whole suite

Seconds, median of 2 runs after a warm-up. Less is better.

vynta81.8 s
vynta, 4 workers82.1 s
Jest, 4 workers241.2 s

With the same number of workers, vynta takes a third of the time. Its run is as long as its slowest file, a file of 114 end-to-end tests that takes about 75 seconds by itself: the other 78 files run next to it.

Once a run is as long as its slowest file, the test code is what is left to make faster. On this suite, replacing fixed sleep() calls by waiting for the database took the run from 82 to 44 seconds.

Where the time goes

A test run is much more than the tests. What each runner spends besides them:

CostJestVitestvynta
Transforming filesBabel, for every fileVite, for every fileNone: Node.js loads them (types stripped by Node.js)
Loading dependenciesAgain for every test fileAgain for every file, by defaultOnce per worker, kept between files
Resolving require()Its own resolverVite's resolverCached between runs
Starting workersA process per workerA thread per file, by defaultA thread per worker, as few as needed
Order of filesSlowest firstSlowest firstSlowest first, on just enough workers
Passing assertionsBuild a matcher object eachA chai assertion eachAbout 0.3 µs each; messages only for failures
Coverageistanbul instrumentationV8, remapped to sourceV8, read directly

The start-up of vynta itself is about 5 ms over starting Node.js. On large projects the biggest cost left is loading dependencies: a backend can load thousands of modules, and resolving each require() probes the file system many times. vynta keeps where it found each of them, and V8's compiled code, in node_modules/.cache/vynta, which halves that time on the runs after the first.

How it was measured

  • Windows 11, Intel Core i7-13700H (6 performance and 8 efficiency cores), Node.js 22.21.
  • vynta 0.1, Vitest 5.0.3 (with @vitest/coverage-v8), Jest 30.2.
  • Each command ran once to warm the disk cache, then 7 times (the library) or 2 times (the backend); the median is shown.
  • Vitest ran with globals: true and a setup file with globalThis.jest = vi, so the Jest tests ran unchanged.
  • vynta ran with its defaults: it chose the number of workers from the previous run.

To measure your own suite, vynta comes with the script used here:

node node_modules/vynta/bench/compare.js 5 \
  "vynta::npx vynta" \
  "vitest::npx vitest run" \
  "jest::npx jest"
