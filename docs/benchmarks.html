Benchmarks

The same test files, unchanged, run by vyntra, Vitest and Jest. Every time is the whole command, from starting it to its exit: what you wait for in your terminal and on CI.

Summary

3.9×faster than Vitest 5 on the tests of NestJS
2.5×faster than Jest 29 on the unit tests of Strapi
1.7×faster than Jest 29 on the tests of Yarn (2.2× with --splitFiles)
2.6×faster than Vitest 5 on a library suite (5.5× Jest 30)

Open-source projects

The test suites of three large open-source projects, run as their repositories have them: no file changed, and vyntra reading the project's own configuration (vitest.config.mts, jest.config.js).

NestJS, with Vitest

nestjs/nest at 7fb52e7: 305 files, 3,701 tests, in TypeScript with legacy decorators and their metadata (which Nest's dependency injection reads), imports of ./file.js that name file.ts, and aliases for its packages.

Both fail the same four files, which import packages missing from the install measured (@fastify/error, fast-querystring, @nats-io/nats-core). Vitest loses one more: a test of shutdown hooks sends SIGTERM to its own process, which on Windows ends the Vitest worker running it, and the 37 tests of that file are not reported. vyntra hands the signal to the test's listeners.

vyntra compiles the TypeScript (with the project's own TypeScript, for the decorator metadata) once and keeps it in node_modules/.cache/vyntra: the cold-cache row is a run with that cache deleted, which compiles every file first.

Strapi, with Jest

strapi/strapi at bc653e8: the unit tests of its 22 packages with a Jest suite, 5,924 tests, in TypeScript compiled by @swc/jest, with shared Jest presets, jest.mock() in many files, and SQLite through knex. Each package runs its own suite, as Strapi's test:unit does, one package after the other, Jest and vyntra taking turns.

The results are the same, test by test, in 20 of the 22 packages, the failures included (12 tests that fail under both on the machine measured). In core/core one test checks a security header the app only sends when NODE_ENV is test, which Jest sets and vyntra leaves as it is. In core/upload two tests expect the MIME detection to be unavailable, as it is under Jest, which can not run the import() of an ES module without --experimental-vm-modules; Node.js runs it, so vyntra detects the type and the expectation fails.

vyntra ran with --pool forks, workers in child processes as Jest's are: on Windows, a worker thread that loaded both SQLite's and swc's native modules can crash the process when it ends. Strapi's packages export their build, so the monorepo was built (yarn build) before either runner ran.

Yarn, with Jest

yarnpkg/berry (Yarn 4) at e4e423a: 44 files, 949 tests, in TypeScript compiled by the project's own Jest transformer (esbuild, to CommonJS), with Plug'n'Play: no node_modules, every package read from a zip archive. Both runners start through Yarn (yarn jest, yarn node vyntra), which takes about 2.8 seconds of each run.

A backend suite

A private Express and MongoDB backend: 79 files, 1,218 tests, 38 jest.mock() calls, end-to-end files that each bootstrap the app against an in-memory MongoDB, Jest 30 with the project's own settings (--maxWorkers=4). Both runners run the same files, and both pass all of them.

Whole suite

Seconds, median of 3 runs after a warm-up, the runners taking turns. Less is better.

vyntra17.9 s
vyntra, 4 workers19.8 s
Jest, 4 workers204.5 s

Part of this gap is the application, not the runner. Jest sets NODE_ENV=test when it is not set; vyntra leaves the environment as it is. With NODE_ENV=test this app mounts its API documentation on every start, scanning the project's files, and every end-to-end file starts the app: run that way, vyntra took between 90 and 135 seconds in our runs, still faster than Jest but by far less. The figures above are each runner as it comes, with nothing set.

Where the time goes

A test run is much more than the tests. What each runner spends besides them:

CostJestVitestvyntra
Transforming filesBabel, for every fileVite, for every fileOnly what Node.js can not run (decorators, JSX, what the project's Jest transform asks for), kept on disk between runs
Loading dependenciesAgain for every test fileAgain for every file, by defaultOnce per worker, kept between files
Resolving require()Its own resolverVite's resolverCached between runs
Starting workersA process per workerA thread per file, by defaultA thread per worker, as few as needed
Order of filesSlowest firstSlowest firstSlowest first, on just enough workers
Passing assertionsBuild a matcher object eachA chai assertion eachAbout 0.3 µs each; messages only for failures
Coverageistanbul instrumentationV8, remapped to sourceV8, read directly

The start-up of vyntra itself is about 5 ms over starting Node.js. On large projects the biggest cost left is loading dependencies: a backend can load thousands of modules, and resolving each require() probes the file system many times, and Node.js looks for the nearest package.json of every file it loads. vyntra keeps where it found each module in node_modules/.cache/vyntra between runs, and the answers about the project's own files in memory for the whole run.

How it was measured

  • Windows 11, Intel Core i7-13700H (6 performance and 8 efficiency cores), Node.js 22.21.
  • vyntra 0.3; Vitest 5.0.2 with @vitest/coverage-v8 (the library) and the versions the projects pin: Vitest 5.0.2 (NestJS), Jest 30.5 (the library), Jest 30.2 (the backend), Jest 29.6 (Strapi), Jest 29.2.1 (Yarn).
  • Every command ran once to warm the disk cache, then 7 times (the library), 5 times (NestJS, Yarn), 3 rounds (Strapi) or 3 times (the backend), the runners taking turns so that a slower moment of the machine weighs on all of them; the median is shown.
  • All the numbers were measured on the same day, 2 October 2026, with the same machine.
  • Each runner ran as it comes, with nothing set: Jest and Vitest set NODE_ENV=test when it is not set, vyntra does not (see the backend suite).
  • NestJS ran as npx vitest run and node path/to/vyntra/bin/vyntra.js, both with the NODE_PATH pnpm's launcher sets; Yarn as yarn jest and yarn node path/to/vyntra/bin/vyntra.js; each Strapi package as node node_modules/jest/bin/jest.js (what its test:unit script runs) and vyntra --config jest.config.js --pool forks, from the package's directory.
  • Vitest ran with globals: true and a setup file with globalThis.jest = vi, so the Jest tests ran unchanged.
  • vyntra ran with its defaults: it chose the number of workers from the previous run.

To measure your own suite, vyntra comes with the script used here:

node node_modules/vyntra/bench/compare.js 5 \
  "vyntra::npx vyntra" \
  "vitest::npx vitest run" \
  "jest::npx jest"
